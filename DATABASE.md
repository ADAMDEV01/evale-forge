# Database schema lifecycle

EvalForge uses Alembic as the authoritative schema-management mechanism. Application
startup verifies connectivity and schema compatibility; it does not create or alter
tables. A database must be initialized or migrated before starting the backend.

## New database

Use an explicitly selected, new empty database target. Do not reuse an existing
database path for initialization.

For example, from the project root in PowerShell:

```powershell
$env:DATABASE_URL = "sqlite:///./evalforge-new.sqlite3"
$env:ALEMBIC_DATABASE_URL = $env:DATABASE_URL
python -m alembic -c alembic.ini upgrade head
python -m backend.app.db.schema_lifecycle --database-url "$env:DATABASE_URL"
python -m uvicorn backend.app.main:app --reload
```

Confirm the target URL and the intended empty database before running `upgrade`.
The compatibility command is read-only; it opens SQLite files in read-only mode.
It reports schema compatibility and Alembic revision state without applying changes.
For PostgreSQL, use a database account with read-only privileges for this check.

`ALEMBIC_DATABASE_URL`, when non-empty, intentionally overrides the Alembic target
only. Otherwise, Alembic uses `DATABASE_URL`; when neither variable is set, both
resolve to the application's file-based SQLite default. Confirm the effective
Alembic target before every migration operation.

The backend container includes `alembic.ini`; when using it, pass its explicit path
(`/app/alembic.ini`) and verify that the configured database target is persistent
and is the intended target before applying a migration.

## Existing database adoption

Never blindly upgrade or stamp an existing database. Existing installations may
have been initialized by `create_all()` and handwritten column additions, and the
presence of all eight application tables does not prove that columns, types,
nullability, keys, constraints, or indexes match the migration history.

After selecting the target explicitly, run the read-only compatibility checker.
It compares the database with an immutable representation of initial revision
`9f75ce1076ac`, not with mutable current ORM metadata:

```powershell
python -m backend.app.db.schema_lifecycle --database-url "<explicit-reviewed-database-url>"
```

Interpret the report as follows:

- **exact_match** means the inspected schema matches current SQLAlchemy metadata.
  It does not itself authorize or perform adoption. If Alembic tracking is missing
  or empty, a separate explicit approval is required before any `stamp`.
- **incompatible** lists detected differences. Do not stamp or upgrade it as the
  initial schema; investigate and create a separate remediation plan.
- **unknown_revision** or another revision that is not the current migration head
  requires manual investigation. Do not overwrite or reset migration history.
- **missing** or **empty** Alembic tracking does not mean the database is empty;
  the checker compares the actual application schema independently.

Before any future authorized migration of a populated database, create a verified
backup and rehearse its restoration. Review the compatibility report and obtain
separate approval for each operation. `stamp` only records a revision; it does not
repair or validate schema differences. The checker never runs `stamp`.

Only after a separate approval explicitly authorizes adoption of an exact match,
and after a verified backup and restore rehearsal, an operator may record the
initial revision on the same reviewed target:

```powershell
$env:ALEMBIC_DATABASE_URL = "<same-explicit-reviewed-database-url>"
python -m alembic -c alembic.ini stamp 9f75ce1076ac
```

For SQLite, retain a separate backup file and rehearse restoring it. For
PostgreSQL, use an approved database backup and restore process. Do not run these
operations against a production target as part of an inspection.

## Future schema changes

Create revisions from the project root and review all generated operations before
use:

```powershell
python -m alembic -c alembic.ini revision --autogenerate -m "describe schema change"
```

Autogenerated revisions are proposals, not verified migrations. Review column
types, nullability, defaults, constraints, indexes, data transformations, and both
`upgrade()` and `downgrade()` before merging. Test every revision against disposable
SQLite and PostgreSQL databases, and rehearse deployment against a restored copy
before applying it to a persistent target.

Apply a reviewed revision only in a controlled deployment after explicitly
confirming the URL:

```powershell
$env:ALEMBIC_DATABASE_URL = "<explicit-reviewed-database-url>"
python -m alembic -c alembic.ini upgrade head
```

Do not use automatic startup migrations. Do not automatically downgrade
production databases. The current initial migration's `downgrade()` drops all
eight application tables and their data; it is destructive and must not be run
against a populated target.
